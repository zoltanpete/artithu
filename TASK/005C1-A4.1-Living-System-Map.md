# Task 005C.1 — Art Direction A4.1: Living System Map / Brand Asset Exploration

## 1. Context

Continue from **A4**. This is **not A5 and not a new redesign direction**. A4 is the current conceptual baseline and has moved the visual language in the right direction.

The owner feedback on A4 is essentially:

> Something has moved. It is getting closer, but it still does not pull strongly enough.

The strongest discovery in A4 is the **system architecture / graph visual in the Hero**. We now want to test whether this can become more than a one-off illustration: potentially a recognizable **ARTIT brand asset** and a recurring visual language for complexity, relationships, processes and structure.

The core brand idea remains:

> **We understand complexity, see through the chaos, and turn it into clear structure.**

A4 communicates precision and systems thinking, but it is currently too quiet. The next experiment should make it more magnetic without making it loud, decorative, gimmicky, or SaaS-like.

---

## 2. Goal

Create **A4.1** as a focused refinement of A4.

The desired character is:

- contemporary;
- premium B2B;
- intelligent;
- calm but confident;
- visually fresh;
- precise;
- technically literate;
- editorial rather than dashboard-like;
- more magnetic than A4;
- recognizably ARTIT rather than generic agency/SaaS.

The conceptual formula is:

**A4 structural intelligence**  
+ **A/A3 editorial elegance**  
+ **a much bolder living system map**  
+ **stronger scale / density / color contrast**  
− **dashboard cosplay**

The important phrase for this iteration is:

> **Magnetic, but controlled.**

## 4. The central experiment: turn the graph into a living ARTIT system map

The Hero graph is the main subject of this task.

In A4 it is conceptually good but visually too small, too polite and too isolated from the rest of the composition.

For A4.1, make it:

- **larger**;
- **bolder**;
- more spatial;
- more layered;
- more colorful within the restrained palette;
- partially cropped by the viewport/container where compositionally useful;
- visually integrated with the Hero rather than sitting inside a separate right-hand illustration zone.

The graph should feel like a **business-system map**, not a flowchart diagram and not a network-analysis application.

It should imply that ARTIT understands not only individual functions but also the relationships between them.

You do not need to use all of these. Choose enough to create meaningful controlled complexity without clutter.

Do not fabricate product features or imply these are screenshots of a real application. This is a conceptual business-system map.

## 5. Show chaos → understanding → structure visually

A4's inputs are still almost as orderly as its outputs. That weakens the emotional story.

A4.1 should make the transformation visible.

The **input / unresolved side** may be:

- more irregularly distributed;
- connected by curved or interrupted paths;
- partially overlapping in depth, but never illegibly;
- made from several kinds of business sources (`EXCEL`, `E-MAIL`, `ADAT`, `KÜLÖN RENDSZER`, etc.);
- composed with some deliberately imperfect routing;
- visually quieter or more fragmented.

The **understood / structured side** should become:

- geometrically cleaner;
- more aligned;
- more intentional;
- connected with straighter paths;
- more strongly associated with the active accent color;
- easier to read at a glance.

The result should communicate without explanatory copy:

**fragmentation → understanding → coordinated system**

Do not turn the left side into literal visual chaos. The whole composition must still feel designed by people who understand structure.

## 6. Break the classic two-column Hero boundary

This is important.

Do **not** merely put a bigger SVG in the current right-hand column.

The system map and the Hero layout should become **one composition**.

Explore techniques such as:

- the graph extending beyond its nominal grid column;
- a few very subtle graph paths entering the whitespace around the typography;
- one node sitting near or across the conceptual boundary between copy and visual;
- portions of the system map cropping off the right or top viewport edge;
- faint coordinate/grid lines spanning a larger portion of the Hero;
- the visual starting or ending at unexpected but carefully controlled positions.

The H1 must remain highly readable and dominant. Never run strong lines through the actual letterforms or make the copy visually noisy.

The desired feeling is not overlap for its own sake. It is that **the entire Hero exists inside one precise system**, rather than two independent web-design columns.

---

## 7. Add one strong visual moment

A4 currently has many tasteful quiet elements but no sufficiently memorable moment.

A4.1 needs **one deliberate visual gesture** that gives the Hero identity.

Possible directions include, but are not limited to:

- one active route travelling through multiple nodes;
- one unusually strong central/focus node;
- a route that crosses a large part of the composition;
- a visually striking transition from loose curved paths into a rigid structured network;
- a focal cluster that changes state interactively.

Choose one coherent solution rather than stacking effects.

The test is:

> If someone saw only a screenshot of this Hero, would there be something recognizably ARTIT about it?

## 8. Interaction experiment — focusable graph

The owner explicitly wants to test a **small amount of meaningful interactivity**.

Implement a restrained graph interaction on desktop/tablet where appropriate.

### Desired interaction model

The graph has a default, beautiful static composition.

On **hover/focus** of an interactive node:

- emphasize that node;
- emphasize its directly relevant relationships;
- gently de-emphasize unrelated paths/nodes.

On **click/tap** of selected major nodes:

- that node becomes the current focus;
- the map may **smoothly rearrange/recenter/recompose** around the selected node;
- relevant connected nodes and paths become clearer;
- unrelated areas recede;
- the result should reveal relationships, not simply animate for spectacle.

Think conceptually of a large graph where selecting a node changes the perspective of the system.

### Keep the interaction intentionally limited

Do **not** add:

- drag-to-pan;
- zoom controls;
- minimap;
- toolbar;
- physics simulation that constantly moves;
- force-directed jitter;
- canvas/WebGL just for effect;
- a graph-library UI;
- tooltip overload;
- gamification.

This is **not a graph explorer**.

It is an editorial system map with a small amount of interaction that reinforces ARTIT's message.

### Motion quality

Movement should feel:

- precise;
- smooth;
- short;
- deliberate;
- mechanically elegant rather than elastic/playful.

No springy SaaS microinteraction style.

Respect `prefers-reduced-motion`: when reduced motion is requested, state changes must remain understandable but re-layout animation should be absent or effectively instantaneous.

Keyboard users must be able to reach and activate interactive nodes, and focus states must be visible.

If full graph rearrangement creates disproportionate implementation complexity or accessibility risk, prefer a simpler deterministic state-transition model over introducing a heavy graph/animation dependency.

**Do not add a graph library or animation dependency unless there is a compelling technical reason. Prefer lightweight native implementation.**

## 9. Color — give the system map more digital energy

Keep the current **Ink / Deep Blue-Violet** direction. Do not start another accent-color search.

The blue-violet should now become part of the ARTIT system language rather than appearing mostly on CTA buttons.

Use restrained tonal levels, for example:

- strongest accent → active/focus node, CTA, one critical system state;
- medium accent → active relationship/path;
- faint tint → selected structural areas, subtle coordinate lines, secondary relationship states;
- graphite / muted neutral → inactive system information.

You may derive tonal variants from the already-used accent if needed, but document them and verify contrast where used for text.

Do **not** introduce a rainbow of node categories.

Avoid generic SaaS blue-gradient aesthetics, neon cyberpunk, terminal-green styling, glowing nodes, glassmorphism or dark-tech spectacle.

We want **digital energy within Swiss restraint**.

---

## 10. Grid / coordinate language

A very subtle underlying coordinate/grid system may help unify the Hero.

Explore this carefully.

It can include:

- sparse horizontal/vertical guide lines;
- coordinate ticks;
- tiny mono coordinates;
- section/system references;
- paths aligning to an invisible structural grid.

But this must remain secondary.

Do not cover the entire page with a graph-paper texture.

The viewer should mostly *feel* the system before consciously noticing the grid.

---

## 11. Problem section — reduce the dashboard feeling

The A4 Hero system-map discovery is stronger than the `DIAGNOSZTIKAI MEZŐ — AKTÍV` interface metaphor.

For A4.1, **move the Problem section slightly back toward editorial elegance**.

Keep its structured/system-thinking character, but avoid making it look like a fake monitoring/dashboard interface.

Retain the asymmetry and controlled density that worked in A4/A3, but simplify the UI-like framing.

Possible direction:

- large editorial H2;
- one denser structured group of four symptoms;
- one quieter open group of two;
- subtle indexing / mono metadata;
- precise rules or alignment;
- tonal field where useful;
- no fake panel header implying an actual application state.

The Hero should be the richest system moment. The Problem section should support it, not compete with it.

Do not revert blindly to A3; reinterpret the best A3 editorial qualities through the A4.1 language.

## 14. Responsive design

Verify at minimum:

- 390px
- 768px
- 1440px
- 1920px

Desktop is allowed to be expansive and partially cropped.

Mobile must **not** simply shrink the desktop system map.

Create an intentionally recomposed mobile version/state. For example:

- fewer visible nodes;
- a smaller set of meaningful relationships;
- 3–4 selectable focus states at most;
- no uncontrolled off-screen interaction;
- simpler path geometry;
- enough breathing room for touch targets.

The mobile experience should still communicate connected systems and focus changes, but with reduced visual complexity.

No horizontal overflow.

## 15. Static-first requirement

Before judging interaction, the default first frame must work as a strong static composition.

Ask:

- Does the Hero pull the eye even before anything moves?
- Does the graph visibly communicate complexity becoming structure?
- Does it feel integrated with the typography rather than attached beside it?
- Does it feel premium rather than like an SVG demo?
- Is there one memorable visual moment?
- Does the blue-violet now feel like part of ARTIT's identity?

Only after the static state works should interaction be considered successful.

Do not use motion to rescue a weak composition.

## 16. Brand-asset test

Treat the system map as a candidate **ARTIT brand asset**.

During visual review, explicitly assess whether the underlying visual grammar could plausibly reappear later in different contexts such as:

- integrations;
- process descriptions;
- project/case-study storytelling;
- feature relationships;
- Tardify ecosystem references;
- section transitions or small branded diagrams.

This does **not** mean implementing those usages now.

It means the Hero visual should be based on a reusable grammar rather than a one-off decorative drawing.

The grammar might consist of things such as:

- node types;
- loose vs structured path behavior;
- active-route accent semantics;
- mono labels;
- focus/recenter behavior;
- coordinate alignment.

Do not prematurely build a large shared component system. First prove the visual language in A4.1.

## 17. Technical / implementation constraints

- Do not change production `/`.
- Do not change prior A/A2/A3/A4/B/C/accent prototype behavior.
- Keep this experiment isolated.
- No fabricated product screenshots.
- Avoid new dependencies.
- Prefer SVG/CSS and minimal native JS where appropriate.
- If client-side JS is required for the focus interaction, keep it small and page-scoped.
- Avoid hydration/framework complexity merely for this prototype.
- No unnecessary network requests.
- No external font requests.
- Maintain semantic heading hierarchy.
- Preserve keyboard accessibility.
- Preserve visible focus states.
- Respect reduced motion.
- Ensure interaction does not depend on color alone.
- Verify text contrast for any newly derived accent/tint usage.

If using SVG interactive elements, ensure they have meaningful accessible names/roles and sensible keyboard behavior. If a parallel semantic control structure is cleaner than making raw SVG nodes interactive, use the more robust accessible solution.
